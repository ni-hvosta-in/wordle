# Как мы работаем

Регламент команды **Wordle Battles**. Здесь записано, откуда берутся задачи, как их брать, как оформлять код и как он попадает в `main`. Если пришёл в команду впервые, начни с [docs/ONBOARDING.md](docs/ONBOARDING.md).

## Роли

| Роль | Что делает |
|---|---|
| **Tech Lead** | Ведёт бэклог, пишет и уточняет задачи, проводит код-ревью, принимает архитектурные решения вместе с командой |
| **Developer** | Берёт задачи, оценивает, реализует, пишет тесты, открывает PR, отвечает на ревью |

## Где живут задачи

Все задачи в **GitHub Issues** этого репозитория, план на доске **GitHub Projects** («Wordle Battles»).

- **Milestone = спринт** (2 недели): `Sprint 1: Фундамент`, `Sprint 2: Играем вдвоём`, …
- **Метки**:
  - тип: `bug`, `feature`, `chore`, `security`;
  - эпик: `epic: foundation`, `epic: multiplayer`, …;
  - оценка: `sp: 1`, `sp: 2`, `sp: 3`, `sp: 5`, `sp: 8`.
- **Колонки доски:** `Backlog` → `Ready` → `In Progress` → `In Review` → `Done`.

### Жизненный цикл задачи
- **Backlog:** идея, ещё не проработана. Брать нельзя.
- **Ready:** есть описание, критерии приёмки и оценка. Можно брать.
- **In Progress:** назначь задачу на себя и перетащи карточку. В работе одновременно **не больше одной** задачи.
- **In Review:** открыт PR со ссылкой на задачу.
- **Done:** PR смёрджен, задача закрылась автоматически.

Если в задаче что-то непонятно или кажется неправильным, пиши комментарий в issue **до** начала работы. Вопрос «а зачем так?» нормальный и правильный. Молча сделать «как понял» гораздо хуже.

## Ветки

- `main` всегда собирается и проходит тесты. Напрямую в `main` не пушим.
- Ветка на задачу: `<тип>/<номер issue>-<коротко>`. Примеры:
  - `fix/3-word-checker`
  - `feature/4-persist-games`
  - `chore/1-flyway`

## Коммиты

Пишем по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/). Номер задачи указываем в футере:

```
fix(game): two-pass letter coloring for repeated letters

Refs #3
```

Типы: `feat`, `fix`, `refactor`, `test`, `chore`, `docs`. Область в скобках — модуль: `game`, `auth`, `challenge`, `db`, `ci`, `front`.
- Один коммит — одно логическое изменение.
- Коммиты вида «wip», «fix», «asdf» перед ревью склеиваем (`git rebase -i`).

## Pull Request

1. Перед открытием подтяни свежий `main`: `git fetch && git rebase origin/main`.
2. Локально прогони `./gradlew build` в `backend` и `npm run lint && npm run build` в `frontend`, если трогал фронт.
3. Заполни шаблон PR. В разделе «Задача» напиши `Closes #<номер>`, тогда после мёрджа задача закроется сама.
4. PR должен быть **маленьким**: ориентир до ~400 строк диффа без учёта миграций и тестовых данных. Если выходит больше, задачу дробим. Скажи об этом в issue.
5. Ревью: замечания помечаются префиксом
   - **blocker:** без исправления не мёрджим;
   - **major:** нужно исправить, можно обсудить как;
   - **nit:** мелочь на твоё усмотрение.

   На каждое замечание отвечаешь: «исправил в коммите X» или «не согласен, потому что…». Тред закрывает тот, кто его открыл.
6. После апрува: **Squash and merge**, ветку удаляем.

## Definition of Done

- [ ] Все критерии приёмки из задачи выполнены.
- [ ] Новая логика покрыта тестами: юнит на бизнес-логику, интеграционный на сценарий через API.
- [ ] CI зелёный.
- [ ] Изменения схемы БД сделаны **только** миграцией Flyway.
- [ ] Нет `System.out.println`, закомментированного кода и TODO без номера задачи.
- [ ] Ошибки отдаются через `GlobalExceptionHandler` с правильным HTTP-статусом, без «голых» 500.
- [ ] Если поменялся API, обновлён фронт или есть отдельная задача на фронт.
- [ ] README обновлён, если поменялся запуск или переменные окружения.

## Стандарты кода

- Внедрение зависимостей только через конструктор, поля `private final`. Подходит `@RequiredArgsConstructor` из Lombok.
- Контроллер тонкий: принял DTO, вызвал сервис, вернул DTO. Логика живёт в сервисах.
- Сущности JPA наружу не отдаём, только `record`-DTO.
- `@Transactional` ставим на публичные методы сервисов. Чтение помечаем `readOnly = true`.
- Магические числа и строки выносим в константы или `application.properties`.
- Логи пишем через `@Slf4j`: `info` для бизнес-событий, `debug` для отладки. Пароли, токены и загаданные слова в логи не пишем.
- Тесты называем по поведению: `shouldMarkDuplicateLetterAsWrong_whenTargetHasSingleOccurrence()`.

## Ритм

- **Спринт — 2 недели.** В начале планирование: берём задачи из бэклога в milestone. В конце ретро: что получилось, что мешало, что меняем.
- **Дейли** асинхронно, раз в день пишешь три строки: что сделал, что делаешь, что блокирует. Застрял больше часа — пиши сразу, ждать дейли не нужно.
- **Оценка в story points** (1, 2, 3, 5, 8): это сложность и неопределённость, а не часы. Задачу на 8 почти всегда надо дробить.
